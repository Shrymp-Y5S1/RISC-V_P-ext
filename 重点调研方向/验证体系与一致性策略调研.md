# 验证体系与一致性策略调研（基于 P-ext-proposal v0.20-draft）

## 1. 调研目标

围绕 P 扩展 v0.20 草案，回答四个可执行问题：

1. 如何从规范内容直接抽出“必须验证”的一致性对象。
2. 如何构建分层验证体系，避免只做单点测试。
3. P 扩展中哪些语义最容易出现一致性偏差，应该优先设断言。
4. 仅靠 `P-ext-proposal.html` 哪些内容不足，必须补哪些外部信息源。

## 2. 证据边界与方法

## 2.1 规范内可直接支撑的内容

`调研材料/P-ext-proposal.html` 可直接提供如下验证输入：

1. 文档状态：`This document is in the Development state. Assume anything can change.`
2. 语义表达框架：`Detailed Instruction Descriptions` 统一采用 `Mnemonic/Encoding/Description`。
3. 形式语义约定：`Sail Code Conventions`（类型、扩展、比较、操作数字段等）。
4. RV32 双寄存器等价规则：`RV32 Double-Register Equivalences` 及其子类规则。
5. 关键状态行为：多处说明 `vxsat is set to 1 if saturation occurs in any element`。

## 2.2 规范内不足以独立完成的内容

仅靠草案无法完整定义以下工程能力：

1. 合规测试框架如何组织（测试筛选、签名对比、报告机制）。
2. 随机验证和覆盖驱动验证的方法论与工具接口。
3. ISA 形式验证接口与属性模板。
4. 参考模型版本管理与差分判责流程。

因此本文件采用“两层证据”：

1. 规范层：定义验证对象与一致性断言。
2. 生态层：引入公开验证框架，形成可执行闭环。

## 3. 从规范抽象出的“一致性对象”

## 3.1 三类基础一致性

由 `Mnemonic/Encoding/Description` 模板可直接定义三类基础一致性：

1. 语法一致性：助记符与操作数格式可正确解析。
2. 编码一致性：同一语义映射到唯一合法编码。
3. 语义一致性：执行结果与描述/伪代码一致。

## 3.2 操作数字段一致性

由 `Instruction Operand Fields` 与 `Register-Pair Notation for RV32` 可定义：

1. `rd/rs1/rs2`（5-bit）与 `rd_p/rs1_p/rs2_p`（4-bit 寄存器对）必须严格区分。
2. RV32 双宽场景中偶寄存器约束必须在前端检查。
3. `x0+ = x0` 语义必须在参考模型、RTL、测试脚本中保持一致。

## 3.3 RV32 等价展开一致性

由 `RV32 Double-Register Equivalences` 可定义“核心判定准则”：

1. `.D*` 指令结果必须等价于 even/odd 两条对应单宽指令组合结果。
2. `.D<S>S` 类要求两次展开共享同一 `rs2`（无 `rs2+`）。
3. `.D<S>S` 两次操作需同时执行，或保证中间不覆盖 `rs2`。

## 3.4 饱和标志一致性

由多处 `vxsat` 说明可定义：

1. 任一 lane 饱和触发时，`vxsat` 必须置位。
2. 多级运算链（如先移位后加法）中，任一阶段触发都应反映到结果标志。
3. 标志位写回时序与可见性应在实现文档中明确（避免 RTL 与 ISS 解释差异）。

## 4. 分层验证体系（建议实施架构）

## 4.1 L0 语义单元层（指令级）

目标：验证每条指令的位级语义正确。

方法：

1. 以规范伪代码/描述建立 Python 或 SystemVerilog 黄金函数。
2. 按元素宽度 B/H/W 与 RV32/RV64 分维度生成边界向量。
3. 先不关心编码与流水，实现“纯语义真值表”。

入口用例：

1. 饱和边界（max+1、min-1、min*min）。
2. 舍入临界位（半位上下）。
3. 横向归约位宽增长场景（2ADD/4ADD）。

## 4.2 L1 编码与汇编一致性层

目标：验证 `Mnemonic -> Encoding -> Disasm` 闭环一致。

方法：

1. 对代表指令构建 round-trip：`asm -> obj -> objdump`。
2. 助记符不可用时用 `.insn` 对照机器码。
3. 非法寄存器对/非法立即数必须稳定报错。

判定：

1. 同输入文本得到唯一编码。
2. 反汇编回显与预期语义族一致。

## 4.3 L2 RV32 等价展开一致性层（P 扩展专项）

目标：证明双寄存器语义与单宽展开严格等价。

方法：

1. 对每类等价规则至少选 2 条代表指令建立差分。
2. 比较对象：
   - 路径 A：执行 `.D*` 指令。
   - 路径 B：执行两条单宽展开指令。
3. 比较结果：数据寄存器、`vxsat`、异常行为。

重点专项：

1. `.D<S>S` 共享 `rs2` 的调度正确性。
2. `x0+ = x0` 特例。

## 4.4 L3 参考模型差分层

目标：让 DUT 与参考模型对同一程序给出一致签名/轨迹。

可选参考：

1. Sail RISC-V 模型（`riscv/sail-riscv`）：正式语义模型，可生成执行模型并支持配置校验。
2. Spike（`riscv-software-src/riscv-isa-sim`）：功能模型，支持广泛 ISA 扩展。

策略：

1. 先做终态签名对比（低成本高吞吐）。
2. 再做指令级轨迹对比（快速定位偏差源）。

## 4.5 L4 架构测试与合规层

目标：通过标准架构测试作为“最低合规门槛”。

公开路径：

1. `riscv-arch-test`（ACT）：
   - 明确其是最小过滤器，不替代完整设计验证。
   - 可生成自校验 ELF，并结合参考模型生成预期结果。
2. RISCOF 文档路径：
   - 给出 DUT 插件与参考插件签名比对流程。
   - 强调架构测试并非完整验证终点。

建议：将 ACT/架构测试作为 `entry gate`，而非 `final gate`。

## 4.6 L5 随机与覆盖驱动层

目标：发现“手写用例难覆盖”的角落组合。

公开路径：`chipsalliance/riscv-dv` 提供约束随机指令流与 ISS 协同对比能力。

建议：

1. 将 P 指令族按风险分层加入随机池。
2. 提供禁止/偏置规则，强化 P0 指令簇触发频率。
3. 以覆盖缺口反向驱动 directed tests 增补。

## 4.7 L6 形式验证层

目标：用形式方法覆盖关键 ISA 属性，提升一致性上限。

公开路径：`SymbioticEDA/riscv-formal`（RVFI 接口 + 指令属性检查）。

建议：

1. 优先对高风险语义族建立属性模板：
   - 饱和上下界约束。
   - 舍入位传播约束。
   - 双寄存器等价展开约束。
2. 先覆盖无特权副作用指令，再扩展到 CSR/异常相关路径。

## 5. P 扩展专项一致性断言清单（可直接转验证条目）

## 5.1 饱和与舍入

1. 对任意 lane，结果必须满足目标位宽上下界。
2. 任一 lane 饱和触发时，`vxsat` 必须置位。
3. 舍入临界样本在 DUT 与参考模型上结果一致。

## 5.2 横向归约与累加

1. 2ADD/4ADD 的 lane 映射和求和顺序与规范一致。
2. ADDA 类读写 `rd` 的旁路行为不应破坏语义。
3. PM2/PM4 与对应展开模型在边界输入一致。

## 5.3 RV32 双寄存器

1. `.D*` 与两条单宽展开结果完全一致。
2. `.D<S>S` 共用 `rs2` 时，两次运算不得被中间写回污染。
3. 偶寄存器约束和 `x0+ = x0` 行为一致。

## 5.4 编码可达性

1. 合法指令文本可稳定汇编。
2. 非法组合（寄存器对/立即数越界）稳定报错。
3. 机器码反汇编不应落到错误语义族。

## 6. 回归组织与判责建议

## 6.1 分层回归节奏

1. 每次提交：L0 + L1 冒烟。
2. 每日回归：L2 + L3 代表子集。
3. 每周回归：L4 全量 + L5 随机长测。
4. 里程碑回归：L6 形式属性集 + 全链路报告。

## 6.2 失败判责顺序

建议按以下顺序排查，减少误判：

1. 配置不一致（ISA/参数/特权开关）。
2. 工具链编码或反汇编偏差。
3. DUT 功能错误。
4. 参考模型版本差异或规范变更。
5. 测试本身假设错误。

## 7. 仅靠 P-ext-proposal 不足时，建议主动补采的信息源

为把“策略”变成“可执行验证计划”，建议你方补齐：

1. 目标 DUT 配置清单：支持扩展、参数、特权级、异常策略。
2. 参考模型策略：使用 Sail、Spike 或双参考并行，及其版本号。
3. 工具链版本：GCC/LLVM/binutils 的 commit 或发布版本。
4. 架构测试配置：ACT/arch-test 所需 YAML、linker、`rvmodel_macros.h`。
5. 覆盖定义：功能覆盖点（特别是 P0 指令簇）与达标阈值。
6. 波形/轨迹策略：签名失败后如何自动切换到 trace 定位。
7. 规范跟踪机制：v0.20 后续变更如何映射到回归用例与黄金模型。

## 8. 组会可直接引用结论

1. `P-ext-proposal.html` 已足够定义 P 扩展“该验证什么”（对象与断言），但不足以独立定义“如何工业化验证”。
2. 最稳妥路径是“六层体系”：语义单元、编码闭环、RV32 等价展开、参考模型差分、架构测试、随机/形式增强。
3. 对 P 扩展而言，双寄存器等价规则、`vxsat` 行为、舍入边界与横向归约是最应优先固化的一致性断言。
4. 架构测试只能作为最低门槛，不可替代完整验证；必须配合随机、差分和形式手段。
